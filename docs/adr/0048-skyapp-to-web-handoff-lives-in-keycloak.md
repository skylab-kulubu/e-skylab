# SkyApp-to-web handoff lives in Keycloak, not in Account center

SkyApp opens SKY LAB websites (first Account center and Forms) inside a first-party WebView, and the person must arrive signed in without a second login. The first version lived in Account center: the app posted its token to `my.`, `my.` minted a one-time URL, started an OIDC flow with a bridge code, and a Keycloak authenticator redeemed that code over an mTLS gateway. That made `my.` a mandatory hop for every site, opened a `my.` session as a side effect, kept a private gateway alive, and could not check that the app's offline session was still alive. The industry products that ship this feature (Okta Native to Web SSO, Auth0 Native to Web SSO) run it inside the identity provider, name the destination by its client identifier, keep the allowlist on the target client's registration, and let the target start its own `/authorize`. We decided to do the same: a `sky-handoff` provider in the SKY LAB Keycloak SPI mints a 45-second single-use code for a skyapp bearer token plus `{target client_id, relative path}`, returns a per-code proof that the WebView must send as a header on its first request, and on redemption establishes the Keycloak browser session (carrying the app's original `auth_time`, replacing another person's session in that browser, marking it as embedded in SkyApp) and redirects to the target's configured sign-in entry. The allowlist is a set of attributes on each target client, changed only through a narrow `sky-handoff` admin endpoint that accepts only the superadmin client's token of a member of the `/ADMIN` group (the same group superadmin and core treat as admin) and that enforces `https://*.yildizskylab.com`. The Account center handoff, the bridge authenticator and the native gateway are removed.

Rejected: extending the Account center handoff with an allowlisted post-login redirect (smaller, but keeps `my.` in every path and diverges from how the vendors do it); Keycloak action tokens (would bypass their completion path, put a JWT in the URL, and hard-fail when another person's cookie is present); Keycloak standard token exchange (never creates a browser session); a free-form target URL checked against an allowlist (OWASP and RFC 9700 favour a server-side mapping of an identifier); giving core `manage-clients` so superadmin could edit client attributes through core (lets core rewrite every client's redirect URIs and secrets).
